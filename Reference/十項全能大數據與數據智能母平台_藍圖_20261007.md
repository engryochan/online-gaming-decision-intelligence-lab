# 2026-10-07 增量｜十項全能大數據與數據智能母平台

> 本章是現有「地緣—軍事—宇航—策略—人工智能—商業化」血統之新增控制層，不刪除任何既有章節。原始問答、歷史判斷與後續更正繼續分層保存；本章只建立一個能容納此前所有資料類型與未來新增資料的通用大數據母平台。

## 0. 母句：全數據不遺漏，不等於所有字節永久熱存

本平台把「一律不許遺漏」定義為：**任何資料進入系統後，不得在沒有可追溯決策的情況下靜默丟棄。**

每一份資料最少必須留下：

1. `asset_id / record_id / event_id`；
2. 原始來源、取得方式、來源時間與擷取時間；
3. 原始內容或依法可保留的不可變指紋／墓碑；
4. Schema / 格式 / 編碼 / 版本；
5. 業務定義與業務擁有人；
6. 事件時間、處理時間、有效時間與失效時間；
7. 空間坐標、CRS、解析度與空間不確定度（若適用）；
8. 品質、完整度、置信度、證據等級；
9. 血統、轉換代碼、依賴與模型版本；
10. 敏感度、法域、授權、許可證、保留與刪除政策；
11. 使用者／下游產品／決策影響；
12. 成本與商業價值。

因此，「不遺漏」= **不靜默遺失 + 不失去上下文 + 不失去血統 + 不失去業務意義**；不是違反 GDPR、PDPA、合約或許可證而永久保存所有個資與第三方內容。

平台的基本資料等式為：

```text
Data Asset
= Raw Evidence
+ Time Semantics
+ Spatial Semantics
+ Schema
+ Business Meaning
+ Ownership
+ Quality
+ Provenance / Lineage
+ Rights / Security
+ Cost
+ Value
+ Decision Effects
```

## 1. 十項全能：平台必須同時具備的十大能力

| # | 能力 | 必須回答的問題 | 建議核心技術 |
|---|---|---|---|
| 1 | **全源接入（Universal Ingestion）** | 資料從哪來？原始內容是否完整進場？ | Kafka / Kafka Connect、Debezium/CDC、Flink、API/Files/Object Store、STAC/OGC、SFTP、Webhook |
| 2 | **不可變原始庫＋開放湖倉（Evidence Vault + Lakehouse）** | 能否重放？能否回到任一歷史版本？ | S3/MinIO/Ceph + Parquet + Apache Iceberg（主）／Delta/Hudi（按情境） |
| 3 | **統一目錄＋業務語義＋本體（Catalog/Semantic/Ontology）** | 這個欄位／事件／人物／設備在業務上究竟代表什麼？ | DataHub 或 OpenMetadata + Business Glossary + Ontology / Knowledge Graph |
| 4 | **品質、證據與血統（Quality/Evidence/Lineage）** | 可不可信？如何生成？誰改過？ | OpenLineage、DataHub/OpenMetadata lineage、dbt/SQL tests、Great Expectations/Soda、hash/signature |
| 5 | **流批一體＋CDC＋事件時間（Streaming/Batch/CDC）** | 現在發生什麼？歷史又如何重算？ | Kafka + Flink；Spark 用於大批量／大型 ML；增量 ETL 優先於全表重算 |
| 6 | **多模態多模型資料平面（Polyglot Data Plane）** | 關係、時序、空間、文本、影像、向量是否都能自然表達？ | PostgreSQL/PostGIS、StarRocks 或 ClickHouse、DuckDB、圖資料庫、向量庫、對象儲存 |
| 7 | **高效計算與統一查詢（Compute & Query Fabric）** | SQL/R/Python 能否在同一血統下高效工作？ | StarRocks/ClickHouse、DuckDB、Polars、Spark、Arrow/Flight SQL、Materialized Views |
| 8 | **AI/ML/Agent 生命週期（AI/ML/AgentOps）** | 模型、特徵、提示詞、Agent、評估能否版本化與回滾？ | MLflow、Feast、PyTorch、ONNX Runtime、Ray（按需）、Prompt/Agent Registry |
| 9 | **治理、安全、韌性與可觀測（Governance/Security/Resilience/Observability）** | 誰能看、誰能改、失敗能否恢復、異常能否追到根因？ | OPA、SPIFFE/SPIRE、OIDC/Keycloak、Vault/HSM、OpenTelemetry、Prometheus/Grafana、immutable audit |
| 10 | **數據產品＋價值賬（Data Product & Value Ledger）** | 這份資料值多少？誰在用？對收入、止損、效率、合規有何增量？ | Data Product Registry、FinOps、Usage Analytics、SLA/SLO、ROI/causal evaluation、API/BI/WebGIS |

這十項不是十個孤立產品，而是一個**控制平面（Control Plane）＋多引擎資料平面（Data Plane）**。最高效率的關鍵不是「只裝一種資料庫」，而是**一份事實、一套血統、一個語義／權限控制面，按工作負載選引擎**。

## 2. 任何資料都要進「全域資料戶籍」：十二大資料族

| 資料族 | 例子 | 原始保存 | 主查詢／服務引擎 | 主要價值 |
|---|---|---|---|---|
| 結構化交易 | 訂單、財務、會員、設備台賬 | Parquet/Iceberg + DB WAL/CDC | PostgreSQL、StarRocks | 財務、營運、風控 |
| 半結構化 | JSON、Avro、Protobuf、XML | Object Store + Iceberg | StarRocks/DuckDB | API、事件、設備 |
| 文本／文檔 | PDF、DOCX、新聞、報告、法規 | Object Store + content hash | Full-text + vector + LLM | 研究、法務、知識 |
| 代碼／配置 | Git、SQL、YAML、IaC、模型配置 | Git/Object Store | Search/catalog | 可重現、審計 |
| 日誌 | App/API/security/audit logs | Object Store | ClickHouse/StarRocks/OpenSearch | 故障、資安、SRE |
| 時序／遙測 | IoT、衛星、氣象、金融 tick | Iceberg/Parquet | Flink + OLAP/TSDB | 即時監測、預測 |
| 事件流 | clickstream、CDC、告警、任務事件 | Kafka log + object archive | Flink/Kafka Streams | 即時決策 |
| 地理空間 | vector/raster/DEM/SAR/COG/STAC | Object Store | PostGIS + GDAL/QGIS/Cesium | GEOINT、土地、物流 |
| 圖與關係 | 人—企業—資產—事件—供應鏈 | Edge/Node export + canonical tables | AGE/Neo4j 等 | 實體解析、關係風險 |
| 影像／音訊／影片 | 遙感、CCTV、錄音、會議、直播 | Object Store | GPU pipeline + catalog | CV、多模態、取證 |
| 向量／Embedding | 文本／影像／圖特徵 | 可重建的源資料 + vector index | pgvector/Qdrant/Milvus | 語義檢索、RAG |
| 模型／特徵／決策 | Features、模型、提示詞、Agent、結果 | Registry + artifacts | MLflow/Feast | 可重現 AI、決策治理 |

### 2.1 一條硬規則：原始資料與索引分離

向量、圖邊、聚合表、物化視圖、特徵表都屬**可重建衍生物**。真正權威的是：

```text
原始證據 → canonical tables/assets → semantic objects → indexes/features/models
```

任何索引壞掉都能重建；任何模型退化都能回到原始證據重新計算。

## 4. 物理架構：一個控制平面，五個資料區

```text
                           ┌──────────────────────────────┐

                                          │
Sources/API/CDC/Files/Sensors/OSINT       │
              │                           │
              v                           v
┌───────────────────────┐      ┌──────────────────────────┐
│ 1. Raw Evidence Vault │ ---> │ 2. Canonical Lakehouse   │
│ immutable + hash      │      │ Iceberg + Parquet        │
└──────────┬────────────┘      └────────────┬─────────────┘
           │                                 │
           │                                 v
           │                      ┌──────────────────────────┐
           │                      │ 3. Semantic/Data Product │
           │                      │ business facts/ontology  │
           │                      └────────────┬─────────────┘
           │                                   │
           v                                   v
┌───────────────────────┐      ┌──────────────────────────┐

└───────────────────────┘      └──────────────────────────┘
```

### 4.1 為何 Canonical 層選開放湖倉

2026-10-07 官方文件顯示 Apache Iceberg 最新文件線為 1.12.0，具備 Schema Evolution、Hidden Partitioning、Partition Evolution、Time Travel、Serializable Isolation、Branching/Tagging、REST Catalog 與多計算引擎整合。這些能力使「資料保存完整＋計算引擎可替換＋歷史可重放」同時成立。

Parquet 則繼續作為主列式交換／存儲格式；2026 年格式版本已到 2.14.0。對大量分析資料，列式壓縮、欄位裁剪與跨語言生態仍是最穩健的共通底座。

## 5. 引擎選型：不要「一庫統天下」，而要有嚴格主從角色

### 5.1 建議核心組合（最少必要集）

| 任務 | 首選 | 原因 |
|---|---|---|
| 物件／冷熱湖倉 | S3-compatible（雲 S3 / MinIO / Ceph） | 成本低、格式開放、解耦計算 |
| Canonical Table | **Apache Iceberg + Parquet** | 版本、演化、time travel、跨引擎 |
| OLTP／Master Data | **PostgreSQL 18.x** | 交易、約束、JSON、OAuth、成熟生態 |
| 空間 Master | **PostGIS** | 地理幾何、索引、Raster/Topology |
| 事件總線 | **Kafka 4.x** | Durable event log / Connect / Streams |
| 流處理 | **Flink** | stateful、event-time、exactly-once、低延遲 |
| 即時 OLAP | **StarRocks 或 ClickHouse，生產主選其一** | 避免雙重運維；以實測 SLO 決定 |
| 單機／邊緣分析 | **DuckDB + Polars** | 低運維、直接讀 Parquet/Iceberg、高效率 |
| 超大批量／大型特徵 | Spark（按需） | PB 級、多節點、生態成熟 |
| 元數據控制 | DataHub 或 OpenMetadata，主選其一 | Catalog、owner、glossary、lineage、data products |

截至 2026-10-07，PostgreSQL 18.6 為 18 系現行維護版本；18 引入 AIO、`uuidv7()`、OAuth 等。StarRocks 官方最新文檔線已到 4.1，定位仍是即時、多維、高併發分析並可直接查詢 Iceberg/Hive/Delta 等湖上資料。DuckDB 1.5 已把 `GEOMETRY` 移入核心，進一步強化本地與邊緣空間分析能力。

### 5.2 Challenger 原則

任何核心引擎都保留 Challenger：

```text
StarRocks <-> ClickHouse
DataHub <-> OpenMetadata
Iceberg <-> Delta/Hudi
Qdrant <-> Milvus/pgvector
Neo4j <-> Apache AGE
Airflow/Dagster <-> Argo/Temporal（按工作流型態）
```

但**同一 workload 在生產只設一個主責引擎**，除非有明確容災／法域／性能理由。避免「為了先進而裝齊天下軟件」。

DataHub 的 Business Glossary 將 Term / Term Group 與實體關聯，並允許 Terms 形成 Contains / Inherits 等關係；其 Metadata Model 以 Entity + Aspect + Relationship 構成 metadata graph。這正適合把既有「人物—組織—資產—事件—地點—天體—數據—模型—決策」升成統一本體，而不是只留在報告文字中。

## 7. 「每一份資料都評估業務價值」：Data Value Card

不要把所有維度硬壓成一個神秘分數；先保留多維向量，再視決策需要加權。

### 7.1 必評十維

| 維度 | 問題 | 0–5示例 |
|---|---|---|
| Decision Criticality | 不看它會不會改變決策？ | 0=無；5=核心決策依賴 |
| Revenue Potential | 可新增多少合法收入？ | 0–5 |
| Loss Avoidance | 可避免多少真實損失？ | 0–5 |
| Efficiency | 可節省多少人時／計算／等待？ | 0–5 |
| Compliance Value | 是否是監管／審計必需？ | 0–5 |
| Reuse | 能被多少產品與團隊重用？ | 0–5 |
| Uniqueness | 是否難以替代／重新取得？ | 0–5 |
| Timeliness | 延遲一小時／一天是否大幅失值？ | 0–5 |
| Quality / Confidence | 是否完整、準確、一致？ | 0–5 |
| Explainability | 能否解釋、追溯、重算？ | 0–5 |

另立四個負項，不與正項混淆：

`AcquisitionCost`、`ComputeCost`、`SensitivityRisk`、`Legal/LicenseRisk`。

### 7.2 資料價值賬的四層證據

1. **存在價值**：有人查、有人依賴；
2. **流程價值**：縮短時間、降低人工、提高成功率；
3. **決策價值**：改變了實際決策；
4. **因果／財務價值**：經 A/B、準實驗、前後對照或可信 counterfactual 證實帶來增量收益／止損／合規改善。

未到第 4 層，不得把「有人使用」直接寫成「創造了多少收入」。

## 9. 全鏈血統：OpenLineage + Metadata Graph + Code/Model Registry

OpenLineage 把 lineage 核心抽象為 `Dataset`、`Job`、`Run`，並以 facets 擴展。平台應再把：

```text
Source → Dataset → Job/Transform → Feature → Model → Prompt/Agent
→ Prediction → Human Decision → Action → Outcome
```

連成一張「證據—計算—決策—結果」圖。

模型部分使用 MLflow Registry 之 model/version/alias/tag 思路；`champion`、`challenger`、`pre_deploy_checks=PASSED` 等都必須是可審計狀態，而不是只看 notebook 裡最後一行結果。

## 10. 可觀測與安全：資料平台本身也是被觀測的資料源

OpenTelemetry 當前把 traces、metrics、logs 作為主要 telemetry signals。平台每一條 pipeline、API、SQL、模型推理、Agent tool call 都必須能關聯到：

```text
trace_id
run_id
dataset_snapshot
model_version
user/workload_identity
policy_decision
cost
latency
result_status
```

### 10.1 身份與政策

- 人：OIDC/SAML + MFA + RBAC/ABAC；
- Workload：SPIFFE/SPIRE；
- Policy-as-code：OPA；
- Secret：Vault/KMS/HSM；
- 高敏操作：雙人覆核／break-glass／不可變日誌；
- 所有高影響 Agent 寫操作：先 policy，再人核，再執行。

SPIFFE 的設計重點是把 workload identity 從 IP/長期 secret 中解耦；SPIRE 可依 process、Kubernetes service account、namespace、Docker 等屬性 attestation 後簽發短期身份文件。

# RedTeam｜十項全能平台最容易如何失敗

1. **資料墳場**：把「不能漏」錯解為「什麼垃圾都永久保存」，最後只有 PB 成本，沒有業務語義。
2. **同名異義**：不同部門都叫 `revenue`、`active_user`、`risk_score`，但公式不同。
3. **時間穿越**：事件時間、入庫時間、有效時間混用，使回測偷看未來。
4. **一庫迷信**：強迫圖、向量、SAR、交易、log、OLTP 全塞同一引擎。
5. **多庫失控**：反過來每種技術都裝，導致 20 個資料副本和 20 個真相。
6. **血統斷裂**：模型只存權重，不存訓練集 snapshot、代碼與特徵版本。
7. **AI 污染來源**：LLM 摘要被重新當原始事實餵回資料湖。
8. **權利污染**：可下載 ≠ 可轉售 ≠ 可訓練模型；License 未進 metadata。
9. **價值幻覺**：Dashboard 點擊量被當 ROI；相關性被當因果增量。
10. **可刪除性與 time-travel 衝突**：法規要求刪除，但 snapshot/backup 還能恢復個資。
11. **Agent 越權寫入**：AI 可查詢後被直接開放 DDL、刪庫、支付、外部發送。
12. **高基數爆炸**：metrics/logs/tags 無治理，觀測系統先把自己拖死。

# Critic｜對「十項全能」的批判

「十項全能」若理解為一套巨大 monolith，是錯的。資料類型和 SLO 天生不同：OLTP 要一致性，流處理要 event-time/state，OLAP 要列式掃描，圖要 traversal，向量要近鄰搜索，GIS 要空間索引，AI 要版本化 artifacts。

所以平台真正的「全能」應是：

> **統一身份、統一目錄、統一語義、統一血統、統一政策、統一價值賬；計算與存儲則按 workload 專用。**

# KillCritic｜為何仍值得建母平台

多引擎並不等於碎片化。只要 canonical data 與 control plane 統一：

- Iceberg/Parquet 保持事實層開放；
- Catalog/Ontology 統一名字與關係；
- OpenLineage 統一血統；
- OPA 統一政策；
- Arrow/Flight SQL/API 統一交換；
- Observability 統一 SLO；
- Value Ledger 統一業務驗收；

底層引擎可以替換而不丟失整個平台的知識與資料主權。

# Blindspot｜最容易被忽略的十四個盲點

1. 資料定義本身會隨業務改變；
2. 相同 ID 跨法域未必可合併；
3. 地理坐標也有精度與時間版本；
4. 氣象／遙感值包含模型或感測誤差；
5. 未知／NULL／0 必須分開；
6. 「無事件」不等於「事件不存在」；
7. Metadata 本身也要備份、版本化與治理；
8. Embedding 會因模型升級失效；
9. Prompt / Agent policy 也是模型資產；
10. API 供應商會改 schema、價格、license；
11. 冷資料重新讀取有 egress/restore 成本；
12. Time-travel 與 legal deletion 必須做政策協調；
13. Synthetic data 不能偷升格成真實證據；
14. Data Product 沒有 owner/SLO/consumer 就不是產品，只是表。

# ActionPlan｜90 日建設順序

## 0–15 日：先立戶籍，不急著建大屏

- 建 `registry_source`、`registry_dataset`、`registry_field`、`registry_business_term`、`registry_license`、`registry_quality_rule`、`registry_value_card`。
- 為現有所有資料逐件補：owner、definition、grain、time semantics、source-of-truth、sensitivity、license、retention、value vector。
- 所有未知資料先列 `UNKNOWN`，不得刪掉或硬猜。

**驗收**：資料資產盤點覆蓋率 = 100%；無 owner/definition 的資產全部能列出缺口。

## 16–30 日：Raw Vault + Canonical Lakehouse

- Object Store；
- Parquet + Iceberg；
- content hash；
- schema registry / data contract；
- quarantine；
- snapshot/time travel；
- 最小備份與恢復測試。

**驗收**：任一 canonical 表可追到原始來源，可重跑，可對同一 snapshot 得同一結果。

## 31–45 日：CDC + Streaming

- DB CDC → Kafka；
- Flink event-time pipeline；
- late event / duplicate / replay 規則；
- Kafka 原始事件定期落 Iceberg。

**驗收**：斷線、重放、亂序、重複注入均不破壞 canonical truth。

## 46–60 日：Semantic + Quality + Lineage

- DataHub/OpenMetadata；
- Business Glossary；
- Entity/Relationship/Ontology；
- OpenLineage；
- Quality Gate；
- 每個 KPI 只留一個 canonical definition。

**驗收**：任一 KPI 能回答「定義、來源、誰負責、由哪些欄位算、哪些產品在用」。

## 61–75 日：Serving + AI

- StarRocks/ClickHouse challenger benchmark；
- PostgreSQL/PostGIS；
- DuckDB/Polars analyst lane；
- MLflow registry；
- 必要時 Feast / vector / graph 插件化加入。

**驗收**：按 p50/p95/p99 latency、吞吐、成本、恢復、正確性，而不是品牌決定勝者。

## 76–90 日：Value Ledger + Data Products

每個資料產品必須有：

```text
Owner
Consumer
Business problem
Canonical metrics
Input assets
SLO
Security class
Unit economics
Decision/action link
Outcome metric
Review cadence
Sunset rule
```

優先把此前已規劃的 GIS 託管、遙感變化監測、Weather→P&L、SupplyGraph/GeoRisk、土地盡調、民用宇航分析做成真正 Data Products，而不是散落 notebook。

## 11. 研究與驗收鐵律

平台選型不採「天下第一」口號，而採：

```text
workload
→ business definition
→ correctness
→ data volume / cardinality
→ freshness / latency SLO
→ concurrency
→ benchmark
→ recovery
→ security / legal / license
→ operating cost
→ business value
→ champion / challenger
```

每季重跑 benchmark；只有當新工具在**同資料、同硬件、同 SLO、同正確性約束**下有顯著收益，才准替換 incumbent。
