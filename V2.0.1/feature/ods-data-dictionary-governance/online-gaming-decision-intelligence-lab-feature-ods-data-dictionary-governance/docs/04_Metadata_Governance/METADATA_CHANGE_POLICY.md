# 元数据变更策略

## 1. 目的

本文件定义在线游戏决策智能实验室（OGDIL）元数据（数据字典、Schema、数据分类、血缘、质量规则等）发生变更时的审批、通知与回滚流程，避免变更在缺乏评审的情况下影响下游系统。

## 2. 适用范围

适用于以下元数据资产的任何新增、修改或删除：

- `docs/03_Data_Dictionary/` 下的数据字典与 Schema 版本文件
- `docs/04_Metadata_Governance/` 下的各项治理规范
- `metadata/` 目录下的分类、血缘、质量、目录（catalog）记录
- ADS 层数据契约（Data Contract）

## 3. 变更分级

沿用《ODS 数据模式版本管理规范》中定义的三级分类，并将其应用于全部元数据资产（不限于 ODS）：

| 级别 | 定义 | 示例 |
|------|------|------|
| 重大变更 | 删除字段/表、修改字段语义、改变关键字段数据类型、调整数据分类等级导致可见范围收紧或放宽 | 将某字段分类由 L1 调整为 L3 |
| 一般变更 | 新增非核心字段、补充业务说明、新增血缘节点 | 为某张 ADS 表新增一个衍生字段 |
| 修订变更 | 文档措辞修正、注释完善、格式调整 | 修正数据字典中的错别字 |

## 4. 审批流程

- **重大变更**：必须提交 Pull Request，至少经过一名数据负责人（Data Owner）与一名下游使用方代表评审通过后方可合并；须在 PR 描述中说明影响范围与下游通知计划。
- **一般变更**：须提交 Pull Request，至少一名评审通过；无需下游使用方额外确认。
- **修订变更**：可直接提交，事后由维护者抽查。

## 5. 变更通知机制

- 重大变更须在合并前至少提前通知已知下游使用方（通过 Issue 或团队内部渠道）；
- 通知内容须包含：变更对象、变更类型、生效时间、是否向后兼容、联系人；
- 涉及数据分类等级调整、可能影响仓库公开范围的变更，须额外抄送仓库管理员确认。

## 6. 回滚策略

- 所有元数据变更均通过 Git 管理，理论上均可通过 `git revert` 回滚；
- 重大变更在合并后的观察期内（建议 7 天）如引发下游问题，可直接回滚并重新走评审流程；
- 回滚操作本身也须遵循本策略中"重大变更"的审批要求。

## 7. 变更记录留存

每一次元数据变更都应在对应资产的版本记录中留存：版本号、变更类型、Git 提交编号、变更摘要、影响范围、审批人。留存记录是《元数据治理框架》中治理台账的组成部分。
