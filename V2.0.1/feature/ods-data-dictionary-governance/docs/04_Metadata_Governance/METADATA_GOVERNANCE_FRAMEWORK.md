# 元数据治理框架

## 1. 目的与定位

本文件是在线游戏决策智能实验室（OGDIL）元数据治理体系的总纲，用于统领以下各项专项规范，说明它们各自的定位与相互关系：

- `docs/03_Data_Dictionary/03_ODS_DATA_DICTIONARY_GOVERNANCE.md` —— ODS 数据字典治理规范
- `docs/03_Data_Dictionary/04_ODS_SCHEMA_VERSIONING.md` —— ODS 数据模式版本管理规范
- `DATA_CLASSIFICATION_STANDARD.md` —— 数据分类标准
- `DATA_LINEAGE_STANDARD.md` —— 数据血缘标准
- `DATA_QUALITY_STANDARD.md` —— 数据质量标准
- `METADATA_CHANGE_POLICY.md` —— 元数据变更策略

## 2. 治理范围

覆盖 OGDIL 数据架构（源系统 → ODS → DWD → DWS → ADS → 应用/模型/仪表盘）中产生的全部元数据，包括但不限于：数据字典、Schema 版本、数据分类、数据血缘、数据质量规则、数据契约（Data Contract）。

## 3. 治理组织与角色

| 角色 | 职责 |
|------|------|
| 数据负责人（Data Owner） | 对所负责的数据域完成初始分类、审批重大变更、对外部咨询负责 |
| 数据管理员（Data Steward） | 日常维护数据字典、血缘记录与质量报告，执行一般变更 |
| 使用方（Consumer） | 通过 ADS 层与数据契约获取数据，发现问题时通过 Issue 反馈 |
| 仓库管理员（Repository Admin） | 把关公开仓库中的数据分类合规性，审核涉及 `.gitignore` 例外的提交 |

在项目当前阶段（v0.1.0），以上角色可由同一人兼任；角色分工将随《ROADMAP.md》中团队规模扩大而正式化。

## 4. 治理体系总览

```
元数据治理框架（本文件，总纲）
    │
    ├── ODS 数据字典治理规范 ── 权威数据源：01/02 号字典 CSV
    ├── ODS 数据模式版本管理规范 ── 版本变化分级（重大/一般/修订）
    ├── 数据分类标准 ── L0~L3 四级分类，决定公开范围
    ├── 数据血缘标准 ── 表级/字段级血缘记录
    ├── 数据质量标准 ── 六大维度 + 分层要求
    └── 元数据变更策略 ── 审批、通知、回滚（适用于以上全部资产）
```

## 5. 治理原则

本框架下所有治理活动须与 OGDIL 章程（`docs/01_Project/OGDIL_Charter.md`）中的科学原则保持一致：

- **可复现**：治理规则本身必须写成文档并纳入版本控制，而非仅存在于口头约定；
- **可解释**：每一项分类、血缘、质量判定都必须可追溯至具体依据；
- **可测试**：质量规则应尽可能转化为可自动执行的检查；
- **可部署**：治理流程须能嵌入日常 CI/CD，而非游离于工程流程之外；
- **可扩展**：治理体系须能随数据规模、团队规模同步扩展，不应假设仅由个人维护。

## 6. 治理成熟度路线

治理体系的落地深度与《ROADMAP.md》各阶段保持同步：

- **v0.2 ~ v0.3（数据底座建设）**：完成本框架下六份规范文档的落地，`metadata/` 目录下建立分类、血缘、质量的初始台账；
- **v0.4（特征存储）**：将治理范围扩展至特征字典，特征的分类与血缘须可追溯至 ADS 层来源；
- **v0.5 ~ v0.6（统计与机器学习实验室）**：模型与实验产出物纳入治理范围，补充模型血缘与再现性要求；
- **v1.0（决策智能平台）**：治理检查全面自动化，接入 CI，人工审批仅保留在重大变更环节。

## 7. 例外处理机制

任何偏离本框架及其下属规范的例外情况（例如临时以 `git add -f` 方式加入被 `.gitignore` 排除的数据文件），必须在对应 Pull Request 中说明理由、影响范围与后续整改计划，并经数据负责人确认后方可合并。例外情况须记录在案，不得作为常态操作。
